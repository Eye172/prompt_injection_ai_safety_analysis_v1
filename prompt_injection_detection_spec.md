# Prompt Injection Detection — техническая спецификация

**Проект:** prompt_injection_ai_safety_analysis
**Область:** AI in Cybersecurity
**Документ описывает:** Вариант E (открытый мультиязычный датасет + две референсные модели: EN и RU) и Вариант A (API поверх этих моделей с выбором языка). Картиночная (typographic) модальность вынесена в конец как задел на будущее — в этой итерации не реализуется.

---

## 0. Общая логика

Вариант A строится **поверх** Варианта E, а не параллельно ему:

```
[Датасеты EN] ──┐
                ├──► [Модель EN (DeBERTa-v3)] ──┐
[Датасеты RU] ──┘                                ├──► [API /detect?lang=en|ru] ──► ответ (score, label, attack_type, span)
                ├──► [Модель RU (DeBERTa-v3)] ──┘
[NotInject / eval-сеты] ──► бенчмарк over-defense для обеих моделей
```

Два **раздельных бинарных классификатора** (не мультиязычная модель на одном чекпоинте) — это осознанное решение: раздельные модели проще калибровать по порогу, легче дообучать независимо (например, обновлять только RU-модель без риска регресса на EN), и не смешивают языковые артефакты токенизации.

### 1.3 Русский слой

**Готовое:**

| Датасет | Ссылка | Особенности |
|---|---|---|
| dmtrdr/russian_prompt_injections | https://huggingface.co/datasets/dmtrdr/russian_prompt_injections | прямые атаки на русском + английский перевод + тип техники + источник (часть синтетика, часть — переведена из Lakera/др.). Apache 2.0 |
| Necent/llm-jailbreak-prompt-injection-dataset | https://huggingface.co/datasets/Necent/llm-jailbreak-prompt-injection-dataset | агрегатор 30+ источников (включает твои SPML, deepset, xTRam1), есть multilingual-срез — годится как источник доп. негативных/позитивных примеров, но не заменяет специализированный RU-корпус |

**Чего нет и придётся генерировать:** одного датасета dmtrdr мало для продакшн-модели (это не тысячи и не десятки тысяч сэмплов уровня xTRam1). План синтетики:

1. Взять категории атак из xTRam1 (context manipulation, social engineering, ignore-prompt, fake completion, role-play jailbreak и т.д.) и PIGuard/NotInject (trigger-word overdefense кейсы) как таксономию.
2. Для каждой категории **сгенерировать нативно на русском** через LLM API (GPT-4o/Claude/YandexGPT) — не переводить английские примеры дословно, а просить модель писать атаку с нуля на русском в этой категории. Дословный перевод даёт модели "переводческий" стиль текста, который не встречается в реальном русскоязычном трафике, и точность на проде проседает.
3. Обязательно сгенерировать русский аналог NotInject: безобидные предложения с триггерными словами ("игнорируй", "новая инструкция", "ты теперь администратор" и т.п.) — иначе RU-модель унаследует ту же болезнь over-defense, которую PIGuard чинит для английского.
4. Отдельно собрать русскоязычные benign-примеры (обычные вопросы, деловая переписка, код-ревью на русском) — источник: можно частично взять из d0rj/ru-instruct или ZeroAgency/ru-big-russian-dataset (huggingface, оба открытые) как negative-класс, если нужен объём быстро.
5. Ручная выборочная валидация (100–200 сэмплов) носителем языка перед тренировкой — автоматическая генерация даёт заметный процент "не атак" под видом атак.

**Казахский:** сознательно не включаем в эту итерацию — по итогам прошлого поиска отдельного датасета под prompt injection на казахском нет (есть только общие safety-датасеты KZ-SafetyPrompts и Qorgau, не про инъекции). Оставляем как Фазу 2 после того, как RU-модель покажет рабочие метрики — методология генерации та же, но потребует привлечения носителя для проверки (автоматическая генерация на казахском даёт больше артефактов, чем на русском).

### 1.4 Пошаговая инструкция создания (Вариант E)

**Шаг 1 — Схема данных.** Привести все источники к единому формату:
```json
{"text": "...", "label": "injection|benign", "category": "...", "language": "en|ru", "source": "dataset_name"}
```
Ты уже это сделал для 5 EN-датасетов ("нормализован" в твоих словах) — применить ту же схему к RU-источникам.

**Шаг 2 — Дедупликация.** SimHash или сравнение эмбеддингов (sentence-transformers) для отсева почти-дублей между источниками — иначе train/test утечка (одна и та же атака в train и в test завышает метрики).

**Шаг 3 — Синтетика RU** — по плану из 1.3.

**Шаг 4 — Балансировка классов.** Целевое соотношение injection:benign — ориентируйся на xTRam1 (3:7), это ближе к реальному трафику, чем 50:50, и снижает false positive rate на проде.

**Шаг 5 — Сплиты.** train/val/test по 80/10/10, **стратифицированно по category и source** (не просто случайно) — чтобы редкие категории атак не исчезли из test-сета.

**Шаг 6 — Резервирование eval-сетов.** NotInject и protectai/prompt-injection-validation **не подмешивать в train** — использовать только для финальной оценки, иначе теряется весь смысл сравнения "мы лучше существующих guard-моделей".

**Шаг 7 — Тренировка EN-модели.** Базовая архитектура: `microsoft/deberta-v3-base` (как у ProtectAI и PIGuard) или `deberta-v3-small`, если приоритет — латентность (у SafePrompt и ProtectAI-small заявлено <100мс). Файнтюн через `transformers.Trainer`, дообучение с MOF-подходом из PIGuard (снижение bias на триггерные слова) — код открыт, можно взять их training loop как отправную точку.

**Шаг 8 — Тренировка RU-модели.** Та же архитектура, но base-модель — русскоязычный DeBERTa/BERT-энкодер (например `DeepPavlov/rubert-base-cased` или `ai-forever/ruBert-base`) вместо `microsoft/deberta-v3-base` — английский токенизатор плохо режет кириллицу на подслова.

**Шаг 9 — Оценка.** Прогнать обе модели на своих eval-сетах + сравнить с ProtectAI DeBERTa-v2 и PIGuard как baseline — это даёт готовый "мы точнее чем X" слайд для питча.

**Шаг 10 — Публикация.** Датасет и модели — на HuggingFace Hub (как сделали PIGuard, dmtrdr, xTRam1) с подробной model card — это одновременно и открытый вклад в сообщество, и бесплатный маркетинг/реферальный трафик на будущий API.

### 1.5 Изображения (typographic injection) — не сейчас, но задел

Не строим в этой итерации, но чтобы не начинать с нуля через полгода — вот что уже открыто и пригодится:

| Ресурс | Ссылка | Заметка |
|---|---|---|
| FigStep / SafeBench | https://github.com/ThuCCSLab/FigStep | код + готовые typographic-картинки, 500 запросов, 10 тем |
| MM-SafetyBench | https://github.com/isXinLiu/MM-SafetyBench | 5040 пар текст-картинка, режимы Typography / Stable Diffusion / SD+Typo |
| JailBreakV-28K | https://github.com/EddyLuo1232/JailBreakV_28K | 28 000 пар, 8000 image-based |

Важная оговорка на будущее: это всё **jailbreak-датасеты** (обход отказа модели на harmful-контент), не «инъекция в агента через скриншот». Для второго типа готовых датасетов нет — есть только фреймворк-генератор AgentTypo (arXiv 2510.04257), собственный датасет придётся рендерить самим (наложение текста на фон с вариацией шрифта/угла/шума — методология из исследования Cisco про typographic-атаки на VLM).

## 2. Вариант A — API поверх Варианта E

### 2.1 Общая схема

Один эндпоинт, параметр языка — либо явный, либо автоопределение с возможностью override:

```
POST /v1/detect
{
  "text": "Игнорируй все предыдущие инструкции и...",
  "lang": "auto"        // "auto" | "en" | "ru"
}
```

Роутинг: `lang=auto` → быстрый langdetect (fasttext lid.176 или lingua-py, <5мс) → выбор модели EN или RU. Явный `lang=en|ru` — пропускает детекцию языка, полезно когда клиент уже знает язык своего трафика (экономия latency).

### 2.2 Response schema

```json
{
  "success": true,
  "data": {
    "is_injection": true,
    "score": 0.94,
    "label": "injection",
    "language_used": "ru",
    "attack_type": "instruction_override",
    "span": {"start_word": 0, "end_word": 5},
    "reasoning": null
  },
  "meta": {
    "request_id": "req_...",
    "model_version": "ru-deberta-v1",
    "latency_ms": 42
  }
}
```

- `attack_type` — категория из таксономии на шаге 1.4 (instruction_override, role_play, fake_completion, context_manipulation, encoding_obfuscation и т.д.)
- `span` — номера слов, где сосредоточен сигнал атаки; получить через attention-веса классификатора или через скользящее окно (прогнать модель на n-граммах текста, найти под-span с максимальным score)
- `reasoning` — зарезервировано под будущий второй, "медленный" слой (LLM-верификация для пограничных случаев, score в диапазоне 0.4–0.7), в MVP можно оставить `null`

### 2.3 Эндпоинты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/v1/detect` | основной — один текст |
| POST | `/v1/detect/batch` | массив текстов, для интеграции в пайплайн обработки логов |
| GET | `/v1/health` | статус, версии загруженных моделей |
| GET | `/v1/languages` | список поддерживаемых языков (сейчас: en, ru) — сделать так, чтобы добавление kz/картинок в будущем не ломало контракт API |

### 2.4 Инструкция разработки

**Шаг 1.** FastAPI-проект, два процесса/воркера модели (EN и RU) загружаются в память при старте, не по запросу — иначе первый запрос на каждый язык будет с задержкой холодного старта.

**Шаг 2.** `POST /v1/detect`: langdetect → выбор модели → `AutoModelForSequenceClassification` + `AutoTokenizer` → pipeline (по образцу кода из PIGuard/ProtectAI карточек на HF) → score → маппинг в response schema.

**Шаг 3.** Attack_type классификация — либо (а) многоклассовая голова на той же модели вместо бинарной (сложнее, но даёт category одним проходом), либо (б) второй лёгкий классификатор поверх эмбеддинга первого (проще встроить постфактум, не трогая уже обученную бинарную модель). Для MVP — вариант (б).

**Шаг 4.** Rate limiting + API-ключи (даже на бесплатном тире) — SafePrompt и ZooClaw в своих API возвращают `creditsRemaining`/`creditsConsumed` в meta, это стандартный паттерн, стоит повторить с самого начала, а не добавлять потом.

**Шаг 5.** Деплой — модели маленькие (DeBERTa-base ~180M параметров), укладываются на CPU-инференс с ONNX-экспортом (ProtectAI публикует именно ONNX-версии своих моделей для этого) — не обязателен GPU-инстанс на старте, это существенно снижает costs.

**Шаг 6.** Логирование запросов (без хранения самого текста, если он потенциально содержит PII клиента — хранить только score/label/category/timestamp) — понадобится и для мониторинга дрейфа качества, и для будущего дообучения на реальном трафике.
